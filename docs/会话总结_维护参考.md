## 二、PaddleOCR 运行时修复

### 2.1 OneDnnContext 错误

**问题**: PaddleOCR 运行时报 `RuntimeError: OneDnnContext does not have the input Filter`

**根因**: PaddlePaddle CPU 和 GPU 版本冲突，ONEDNN 兼容性问题

**解决方案**:
1. 卸载 CPU 版本 PaddlePaddle
2. 安装 `paddlepaddle-gpu==3.3.0`
3. 禁用 ONEDNN：设置环境变量 `FLAGS_use_mkldnn=0`

**影响文件**: `subtitle_engine.py` 中的 OCR 初始化部分

### 2.2 "未识别到字幕" 错误

**问题**: 程序静默失败，报告 "未识别到字幕" 但无详细错误信息

**根因**: OCR 识别循环中异常被静默吞没

**解决方案**:
1. 为前 3 个 OCR 失败添加错误日志记录
2. 实现 GPU → CPU 自动降级回退机制

**影响文件**: `modules/subtitle_engine.py`

### 2.3 PaddleOCR 环境配置

- PaddleOCR 虚拟环境路径: `D:\Software\PaddleOCR_gpu\venv`
- 环境变量: `PADDLEOCR_VENV`
- 启动脚本 `启动.py` 自动检测 PaddleOCR 虚拟环境和 FFmpeg

### 3.2 P0 #1：整理阶段文本替换 Bug

**问题描述**: 用户怀疑字幕整理阶段存在文本替换（覆盖）问题

**排查结论**: 代码已正确使用 `append` 而非替换，**无需修复**

> **⚠️ 关键结论**: `_organize_subtitles` 方法在合并字幕时使用追加逻辑，不会用新文本覆盖已有文本。这是正常行为，非 Bug。
>
> 通俗解释：当 OCR 从连续的帧中识别到同一个字幕的多个片段（如 "今日は" → "今日は良い" → "今日は良い天気"），程序不会后半段替换前半段，而是追加补充。

### 3.3 P0 #2：翻译失败无感知 ⭐

**问题**: 翻译过程中无法区分成功/失败，用户不知道是否有字幕翻译失败

**解决方案**:
- 修改 `_translate_subtitles` 方法，返回 `Tuple[List[SubtitleItem], int, int]`
- 第一个 `int` 为翻译成功数，第二个为翻译失败数
- `ProcessResult` 新增 `translated_count` 和 `failed_count` 字段
- GUI 在完成时显示翻译成功/失败统计

**关键代码** (`subtitle_engine.py`):
```python

    if not self.translator:

    untranslated = [sub for sub in subtitles if not sub.translation]
    total = len(untranslated)
    
    if total == 0:
        return subtitles, 0, 0

    batch_size = 10
    success_count = 0
    failed_count = 0
    # ... 批量处理逻辑 ...
    return subtitles, success_count, failed_count
```

**影响文件**:
- `modules/subtitle_engine.py` — 核心修改
- `modules/main_window.py` — 显示统计结果
- `config/config.example.json` — 新增配置项

## 四、字幕整理算法优化讨论 ⚠️

### 4.1 当前算法：Jaccard 相似度

- 计算两个字幕文本字符集合的 Jaccard 指数
- 阈值: 0.8（在 `config.example.json` 的 `subtitle.similarity_threshold` 中配置）

### 4.2 提议算法：Levenshtein 编辑距离

**区别分析**:

| 维度 | Jaccard | Levenshtein |
|------|---------|-------------|
| 原理 | 基于字符集合的交集/并集比 | 基于字符插入/删除/替换的最小操作数 |
| 优势 | 计算快速 | 保留字符顺序信息，对递进字幕更准确 |
| 劣势 | 丢失顺序信息 | 计算量略大 |
| 场景适配 | 乱序文本比较 | 有序文本（字幕场景）更好 |

**示例差异**:
- "今日は" vs "今日は良い天気" → Jaccard: ~0.50（低），Levenshtein 归一化: ~0.75（高）
- 对递进式字幕，编辑距离更能反映真实相似性

### 4.3 测试用例调整需求

如果替换为 Levenshtein，现有测试 `test_p0_fixes.py` 中的用例需要调整：
- `test_text_merging_instead_of_replacement` — 阈值可能需要微调
- `test_not_similar_creates_new_entry` — 验证完全不同文本的区分
- 需新增 Levenshtein vs Jaccard 差异场景用例

### 4.4 状态

**仅讨论，未实施代码改动。** 阈值从 Jaccard 的 0.8 调整为适合 Levenshtein 的值需要实际测试验证。

## 八、重要决策记录

### 决策 1：PaddleOCR 环境隔离

- **决定**: 使用独立虚拟环境 `D:\Software\PaddleOCR_gpu\venv` 运行 PaddleOCR
- **依据**: PaddlePaddle 依赖庞大（CUDA、cuDNN），与主项目隔离可避免依赖冲突
- **时间**: 早期决策

### 决策 2：翻译失败处理策略

- **决定**: 翻译失败时原文字幕保留为空，通过统计告知用户失败数，而非反复重试或报错中断
- **依据**: 避免单条翻译阻塞整个批处理流程，用户可事后手动补翻译
- **时间**: P0#2 修复阶段

### 决策 3：项目命名规范

- **决定**: 主项目目录使用 `AVT_Subtitle_Processor`（大写下划线），而非小写 `avt_subtitle_processor`
- **依据**: 与 GitHub 仓库名 `AVT_subtitle_processor` 区分，Windows NTFS 下不冲突
- **风险**: 同时存在大小写版本会导致 Git 混淆——已通过删除小写目录解决

### 决策 4：启动方式统一

- **决定**: 统一使用 `启动.py` 作为唯一启动脚本，废弃 `run.bat`、`start.bat`、`start.py`、`启动.vbs`
- **依据**: `启动.py` 提供自动环境检测、FFmpeg 验证、详细错误提示
- **时间**: v2.1.0

### 决策 5：GitCode ↔ GitHub 双向同步

- **决定**: 通过 `.github/workflows/` 自动化同步代码和 Release 资产
- **依据**: 国内网络限制 GitHub，GitCode 作为国内镜像
- **时间**: v2.1.0

    start: float          # 开始时间（秒）

## 十一、潜在风险与应对建议

### ⚠️ 风险 1：代码可能丢失

**风险**: 当前 `AVT_Subtitle_Processor/` 从 GitCode 恢复，可能不含对话中修改的代码

**建议**:
- 检查 `subtitle_engine.py` 的 `_translate_subtitles` 返回值是否为 `Tuple`
- 检查 `config.example.json` 是否包含 `show_translation_only` 配置
- 对比 GitHub 和 GitCode 的差异

### ⚠️ 风险 2：Levenshtein 算法替换

**风险**: 阈值不匹配可能导致字幕整理异常（过度合并或过度拆分）

**建议**:
- 先在小数据集上测试 Jaccard 0.8 vs Levenshtein 不同阈值的效果
- 建议 Levenshtein 归一化相似度阈值从 0.6 开始测试
- 更新 `test_p0_fixes.py` 测试用例

### ⚠️ 风险 3：路径硬编码

**风险**: `启动.py` 中包含硬编码路径 `D:\Software\PaddleOCR_gpu\venv`

**建议**: 确保其他开发者/用户文档中包含修改此路径的说明

### ⚠️ 风险 4：FFmpeg 二进制文件管理

**风险**: 两个 ~97MB 的 exe 文件不提交 Git，新开发者可能遗漏

**建议**: `bin/README.md` 和 `docs/FFMPEG打包准备.md` 提供清晰下载说明

### ⚠️ 风险 5：PaddlePaddle 版本锁定

**风险**: `paddlepaddle-gpu>=3.3.0` 可能与未来 CUDA 版本不兼容

**建议**: 记录当前测试通过的环境组合：
- CUDA 12.x + paddlepaddle-gpu 3.3.0 + PaddleOCR 2.8.1
- 新环境部署前先在测试环境验证
